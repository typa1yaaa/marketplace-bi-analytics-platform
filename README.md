# Marketplace BI Analytics Platform

**Сквозная BI-платформа для анализа метрик маркетплейса, обнаружения аномалий и исследования их влияния на бизнес.**

Проект моделирует аналитическую инфраструктуру онлайн-маркетплейса: генерирует синтетические данные, загружает их в PostgreSQL, преобразует с помощью dbt в аналитические витрины, выявляет отклонения ключевых метрик и исследует возможные причины их возникновения.

Проект демонстрирует практическую работу с SQL-аналитикой, трансформацией данных, определением KPI, анализом конверсий, обнаружением аномалий, исследованием их распределения, контролем качества данных и автоматизированным тестированием сквозного аналитического пайплайна.

## Цели проекта
- Генерация воспроизводимых синтетических данных маркетплейса.
- Организация слоя исходных данных в PostgreSQL.
- Преобразование данных в staging-модели и аналитические витрины с помощью dbt.
- Расчет бизнес-метрик, конверсий и скользящих показателей.
- Обнаружение аномальных изменений ключевых метрик.
- Исследование распределения аномалии по категориям, регионам и платформам.
- Контроль качества данных и проверка корректности аналитических расчетов.
- Автоматизация тестирования и проверки пайплайна с помощью GitHub Actions.
- Подготовка данных для дальнейшего анализа и визуализации в Apache Superset.

## Модель данных

Генератор создает синтетические данные за 90 дней работы маркетплейса. Фиксированный seed позволяет воспроизводить результаты генерации и повторять проверки.

| Набор данных | Содержание |
|---|---|
| `users` | Пользователи, даты регистрации, регионы и платформы |
| `listings` | Объявления, категории, цены и продавцы |
| `events` | Показы, просмотры объявлений и контакты |
| `deals` | Сделки, связанные с контактами, их суммы и статусы |

Данные включают шесть категорий маркетплейса, несколько регионов и три платформы: Android, iOS и Web.

### Слои данных

**Raw (`raw`)**

Хранит исходные наборы данных, загруженные из CSV-файлов в PostgreSQL.

**Staging**

Подготавливает данные к аналитике: стандартизирует поля, вычисляет даты событий, обогащает события атрибутами объявлений и обрабатывает дубликаты идентификаторов событий.

**Analytics (`analytics`)**

Содержит агрегированные показатели и аналитические витрины для мониторинга KPI, обнаружения аномалий, анализа их распределения и контроля качества данных.

## Аналитика и обнаружение аномалий

### 1. Расчет бизнес-метрик

Платформа рассчитывает ежедневные показатели маркетплейса:

- Количество показов, просмотров и контактов.
- Количество созданных и завершенных сделок.
- GMV - суммарную стоимость завершенных сделок.
- Конверсию из показа в просмотр и из просмотра в контакт.
- Скользящие семидневные показатели конверсии и GMV.
- Когортные показатели конверсии.

Определения метрик и логика агрегации реализованы в SQL и моделях dbt.

### 2. Обнаружение аномалий

В синтетические данные намеренно заложен сценарий изменения бизнес-метрики.

**Сценарий:** в последние 14 дней датасета снижается вероятность того, что пользователь свяжется с продавцом после просмотра объявления в категории Electronics.

Алгоритм обнаружения аномалий:

1. Рассчитывает ежедневную конверсию отдельно по категориям.
2. Формирует исторический базовый уровень на основе предшествующих 28 дней.
3. Вычисляет отклонение от базового уровня с помощью z-score.
4. Помечает наблюдения, превышающие порог аномалии, при наличии достаточной истории.
5. Оценивает количество потенциально потерянных контактов относительно исторического базового уровня.

Для обнаружения требуется не менее 14 исторических наблюдений. Аномалией считается отклонение с абсолютным значением z-score больше 3.

### 3. Анализ распределения аномалии

Обнаружение отклонения - только первый шаг. Далее платформа исследует, в каких сегментах сосредоточено изменение метрики.

Для этого сравниваются недавний 14-дневный период и предшествующий 28-дневный базовый период. Анализ проводится в разрезе:

- Категорий маркетплейса.
- Географических регионов.
- Пользовательских платформ.

Для каждого сегмента рассчитываются изменение конверсии, оценка потерянных контактов и доля сегмента в общей оценке потерь.

Сквозные тесты проверяют, что смоделированное снижение локализуется в категории Electronics: на нее приходится более 90% оцененных потерь внутри соответствующего сравнения по категориям. При этом разрезы по регионам и платформам не должны объяснять аномалию аналогичным образом.

### 4. Контроль качества данных

Витрина качества данных отслеживает ежедневные объемы исходных и подготовленных событий, а также выявляет:

- Потери строк при преобразовании данных.
- Неожиданные изменения дневного объема событий.
- Недостаток исторических данных для проверки объемов.

Такой контроль помогает отличать реальное изменение поведения пользователей от потенциальных проблем обработки данных.

## Быстрый запуск

### Требования

- Docker и Docker Compose.
- Python 3.11 или новее.
- Git.

### 1. Клонирование репозитория

```bash
git clone https://github.com/typa1yaaa/marketplace-bi-analytics-platform.git
cd marketplace-bi-analytics-platform
```

### 2. Запуск PostgreSQL

```bash
docker compose up -d postgres
```

Дождитесь, пока база данных перейдет в состояние готовности.

### 3. Установка зависимостей Python

Создайте виртуальное окружение:

```bash
python -m venv .venv
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Установите зависимости:

```bash
python -m pip install -r requirements.txt
```

### 4. Генерация данных

```bash
python -m src.generator.generate --out data
```

Генератор создаст CSV-файлы пользователей, объявлений, событий и сделок.

### 5. Загрузка данных в PostgreSQL

```bash
python -m src.loader.load --data data
```

Загрузчик применяет схему базы данных и загружает наборы данных в схему `raw`.

**Важно:** перед загрузкой исходные таблицы очищаются. Используйте команду с базой данных разработки, а не с данными, которые необходимо сохранить.

### 6. Построение аналитических моделей

```bash
cd dbt
dbt build --profiles-dir .
cd ..
```

Команда строит staging-модели и аналитические витрины, а затем выполняет настроенные тесты dbt.

### 7. Запуск аналитического отчета

```bash
python -m src.report
```

Отчет выводит сравнение KPI, обнаруженные аномалии, результаты анализа их распределения и сводку качества данных.

## Apache Superset

В проект включена Docker-конфигурация Apache Superset с подключением к PostgreSQL.

Запустите Superset:

```bash
docker compose --profile bi up -d --build
```

Откройте [http://localhost:8088](http://localhost:8088).

В локальной конфигурации используется учетная запись `admin` с паролем `admin`. Измените учетные данные перед использованием сервиса за пределами локального окружения.

Подключение к базе данных настраивается автоматически. Таблицы из схемы `analytics` можно использовать в качестве источников для дашбордов мониторинга KPI, анализа конверсии и исследования аномалий.

## Тестирование

Проект включает модульные тесты, проверки SQL-расчетов и сквозные тесты.

Запуск тестов генератора и SQL-аналитики:

```bash
python -m pytest -q tests/test_generator.py tests/test_sql_analytics.py
```

После генерации и загрузки данных, а также построения моделей dbt, запустите сквозные тесты:

```bash
python -m pytest -q tests/test_e2e.py
```

Тесты проверяют:

- Корректность расчета KPI на контрольных примерах.
- Расчет конверсий и показателей воронки по категориям.
- Обнаружение намеренно внесенной аномалии.
- Локализацию смоделированного снижения в ожидаемой категории.
- Согласованность SQL-детектора и модели обнаружения аномалий в dbt.
- Результаты проверок качества данных на чистом сгенерированном наборе.

GitHub Actions автоматизирует основные этапы пайплайна: установку зависимостей, SQL-тесты, генерацию и загрузку данных, выполнение `dbt build`, сквозные проверки и запуск аналитического отчета.

## Ограничения

- Используются синтетические данные, предназначенные для демонстрации и тестирования, а не для реального бизнес-прогнозирования.
- Аномалия намеренно внесена в данные для проверки алгоритмов обнаружения и анализа.
- Статистическое отклонение от базового уровня само по себе не доказывает причинно-следственную связь.
- Оценка потерянных контактов является контрфактической оценкой относительно базовой конверсии, а не непосредственно наблюдаемым количеством потерянных сделок.
- Локальное окружение Docker Compose предназначено для разработки и демонстрации, а не для промышленной эксплуатации.
